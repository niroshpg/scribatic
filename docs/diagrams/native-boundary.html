Why the NDK is not optional

Four requirements sit below the ART boundary. None of them has an equivalent above it — not because of how the code is written today, but because of what the JVM can and cannot reach.

Premise 01

ggml backends

whisper.cpp and llama.cpp carry hand-written ARM intrinsics — SDOT, UDOT, FP16 FMLA. No JVM path emits them: there is no Java intrinsic, and the JIT will not synthesise dot-product instructions from a Kotlin loop.

The managed-language alternatives — ONNX Runtime, LiteRT, MediaPipe — are themselves .so files crossing the same ABI. They stop you writing C++, not shipping it.

Wired · whisper decoding on device

Premise 02

sqlite-vss + faiss

Vector search is a loadable SQLite extension written in C++ over faiss. Android's platform SQLite does not permit extension loading, and Room and SQLDelight both sit on top of it.

On-device ANN therefore means bundling your own SQLite and linking the extension — an NDK requirement that survives to the shipped product, not a scaffolding detail.

Planned · schema defined, nothing linked

Premise 03

Model residency

A 1.2 GB GGUF must stay clean, file-backed and evictable. FileChannel.map() does give you mmap from Kotlin, but it caps a single mapping at Integer.MAX_VALUE and exposes no madvise.

ggml needs a raw pointer into the mapping regardless, so the allocation decision cannot live above the boundary even where the JDK offers a partial equivalent.

Wired · called from warmUp()

Premise 04

AAudio capture

AAudio is an NDK-only C API. AudioRecord is the managed counterpart and is what runs today — a blocking read on a JVM thread, subject to GC scheduling.

When the realtime callback path lands, capture moves below the line and the lock-free ring buffer finally guards what it was designed to guard. This premise strengthens as the work completes.
